Expanding Wild

A practical reference for the current five-reel prototype: what the game does, where its math lives, and how a balance package can move from Excel into the simulator.

Game overview

5 × 5Five reels, five visible rows
15 linesLeft-to-right paylines
10 symbolsT1–T5 and L1–L5 regular pays
5 free gamesAwarded on three or more scatters
100× capMaximum win per basegame round

Each reel stops on a circular strip. After the stop, the selected set may insert special symbols into eligible visible cells. A banner makes its reel wild for win evaluation. Wins start on reel one and continue left to right; configured payline wins are resolved once per line using the highest final payout.

The values shown on this page describe the current Java defaults. They are example math and should not be treated as a production balance.

Features and spin flow

Basegame

Each base spin draws one of two sets using a 3:1 relative weight (set 0:set 1). Set 0 can insert scatters on reels 1, 3 and 5. Set 1 can insert banners across all reels. Insertions are applied after the reel stops.

Scatter freegame trigger

Three visible scatters trigger five free spins. Scatter insertion is limited to at most one per eligible reel. Freegame sets have no scatter insertion rule, so freegames do not retrigger under the current configuration.

Expanding banner wilds

A banner expands to fill its reel with wilds after the stop and insertion stages. In freegame set 1, each visible banner receives a multiplier from that set’s weighted multiplier table. Multipliers on a winning line add together; a banner contributes only when it is part of that line’s winning prefix. Basegame banners use 1×.

Round win cap

The basegame win and subsequent freegame wins share a round cap of 100 times the round stake. A spin that reaches the cap is clipped to the remaining amount, and later free spins are skipped.

Recommended Excel-to-simulator workflow

  1. Balance in the workbook.
    Use named sheets and stable IDs for symbols, modes, sets, reels, stops, paytable, paylines, feature weights and shared values.
  2. Export a versioned JSON config.
    A small exporter reads workbook tables and writes a portable data file. Java should load the exported config, not depend on Excel at runtime.
  3. Validate before simulation.
    Check required fields, duplicate IDs, strip lengths, valid symbols, nonnegative weights, valid references, and that each weighted table has positive total weight.
  4. Run and record the balance.
    Save the config version or hash, simulator revision, seed, rounds and key RTP/feature statistics beside every result.

This keeps the workbook useful as the authoring UI while JSON remains an open handoff format that can be generated by another tool or employer’s pipeline later.

Balancing handover package

A reviewable delivery should include the math inputs, the exact simulator build used, and evidence that the target values were checked.

1. Balance workbookVersioned sheets, units, IDs, source notes and change log.
2. Exported configJSON plus schema/version and workbook revision reference.
3. Validation reportInput checks, warnings and any unresolved assumptions.
4. Simulation reportRTP split, hit rate, volatility, feature trigger/return, win cap and seed.
5. Reproducibility detailsSimulator commit/version, configuration hash, rounds, stake, seed and thread/partition settings.
6. Known limitationsPayline/stake interpretation, simplified mechanics, omitted features and confidence limitations.

For a new team, keep the workbook format documented and the JSON schema stable. The receiving team can replace the exporter or workbook tooling without rewriting game math, provided it produces the same validated config contract.

Implementation status and limits

  • Implemented: reel strips, weighted Basegame/Freegame set selection, weighted symbol insertion, scatter trigger, expanding banner wilds, additive line multipliers, payline evaluation and round win cap.
  • Replay records include selected sets, reel stops, inserted locations and resolved banner multiplier choices.
  • The current full reelset evaluator covers the regular reel/paytable cycle only. It skips random insertions, scatters, banner expansion and multipliers, so it is not a full feature-inclusive PAR result.
  • The existing defaults are intentionally simple. No claim of target RTP, volatility, hit frequency or production readiness is made by this page.
