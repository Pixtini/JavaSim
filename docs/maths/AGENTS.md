# Instructions for mathematical documentation

Set the instructions for writing and using the maths documents.

# Overview

This /maths provides a hub for the repeated game rules and mechanics and unspoken rules for games, this folder is to be used in conjunction with the Game Design Documents. 

- 01_FUNDAMENTALS - Is the core elements of what makes a slot
- 02_GAME_MODES - Breaks down each mode and their purpose
- 03_WIN_EVALUATION - Breaks down win evaluations and how they are to be implemented
- 04_MECHANICS - Features individual mechanics and some of their interactions, this space will be updated frequently

Each documentment will have its rules with a code XXX-YYY, and some examples, these examples may not apply for every implementation.

# Important 

- When discussing please reference the codes where possible.
- Do not modify this folder or its contents, unless specifically told
- If Infomation appears incorrect, incomplete or outdated, report the issue rather than mofifying the source.
- Using the maths folder:
    Before beginning a task:
    1. Determine whether the knowledge hub contains relevant information.
    2. Read the relevant documentation before making implementation decisions.
    3. Consult the GDD or task specification.
    3. Follow applicable project conventions and requirements.
- Do not read the entire knowledge hub unnecessarily.
- Retrieve information relevant to the current task.
- This folder is the authoritative reference for documented maths/feature conventions.
- Distinguish between:
    * Required rules.
    * Recommended approaches.
    * Configurable behaviour.
    * Illustrative examples.
    Examples are not automatically requirements.
- Avoid Assumptions, never invent rules that are not listed here or in GDD, have the user update the sources or resolve directly with 
- Do not treat the absence of a rule as permission to invent one.

# Final Principles

* Read before implementing.
* Follow documented conventions.
* Respect the scope of each rule.
* Never invent missing requirements.
* Never modify the knowledge hub without permission.
* Report contradictions and missing information.
* Maintain traceability between documentation and implementation.
